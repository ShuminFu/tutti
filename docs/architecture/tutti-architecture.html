ShuminFu / tutti · Architecture

An Electron shell conducting a local Go daemon

Tutti is a local-first desktop product: everything meaningful — business rules, durable state, agent lifecycles — lives in a long-running Go daemon called tuttid on the user's machine. The Electron app is deliberately kept a thin shell that supervises the daemon and renders its state. One repo holds both worlds: a pnpm workspace for TypeScript and a go.work workspace for Go.

The big picture

Process topology

Three kinds of processes run on the user's machine: the Electron app, the tuttid daemon it supervises, and the agent provider processes (Claude Code, Codex, Cursor, …) that tuttid's agent stack launches. The CLI is a fourth, occasional visitor that speaks to the same daemon API.

Startup

How the shell finds its daemon

The renderer never hardcodes an endpoint and never discovers one itself — supervision is exclusively a main-process job. The handshake is a real sequence:

main spawns tuttid, asking it to bind 127.0.0.1:0
The OS picks a free port; nothing is assumed in advance.
tuttid publishes its listener info
Actual bound address + a per-run bearer token are written to <state-dir>/run/tuttid.listener.json.
main reads it and hands resolved backend config to renderer windows
Renderer gets an origin and a token — never lifecycle knowledge.
renderer builds one canonical @tutti-os/client-tuttid-ts client
Its restart-aware fetch re-resolves the backend config before every request, swapping only the origin and the Authorization header — so a daemon restart is invisible to feature code.

The central discipline

One business core, kept that way on purpose

The repo's most repeated rule: the desktop app must never become a second business core. Every layer of tooling below exists to keep this division honest.

services/tuttid owns the product

Business rules, domain workflows, durable state, the HTTP/query API, and adapter surfaces. Long-running; survives across windows.

  • State transitions and domain decisions land here first
  • Contract changes start in the OpenAPI spec, not in code
  • Embeds built-in apps (e.g. onboarding) as generated assets

apps/desktop owns the glass

Electron lifecycle, daemon supervision, the preload bridge, window composition, and renderer feature modules.

  • Feature logic lives in feature-local services; services/internal/** is private to its feature
  • Calls tuttid or IPC adapters instead of re-implementing workflows
  • UI is built from @tutti-os/ui-system; all copy goes through i18n
Litmus test used throughout the repo: if a change needs a domain decision or a state transition, it belongs in tuttid — the desktop may only present it.

Transport

Four lanes, each with one job

Business traffic and host capabilities travel on deliberately separate paths. The event stream is schema-first: contracts in packages/events/protocol generate typed code for both the Go and TypeScript sides.

HTTP renderer / CLI → tuttid
Ordinary request–response business APIs, defined by the OpenAPI contract, authenticated with the per-run bearer token.
Business-event WebSocket renderer ⇄ tuttid
One bidirectional, typed event stream for product coordination — replacing scattered route-local pub-sub. Validated against JSON Schema on both ends.
Terminal WebSocket renderer ⇄ tuttid · one per session
A raw byte stream with PTY control frames (input/resize/gap/exit) — deliberately not multiplexed onto the typed event bus, whose protocol must stay narrow.
Electron IPC renderer → preload → main
Host capabilities only — OS integration, window control, daemon supervision. main never becomes a general event relay for business data.

The most important invariant

The Agent Host boundary

Agent lifecycle semantics — when a session, turn, goal, or runtime-operation is created, when it may be sent, when it's terminal, how it recovers — have exactly one owner. Everyone else is an adapter.

tuttid agent adapter services/tuttid/service/agent

Other hosts e.g. tsh

packages/agent/host Go — the single lifecycle owner
New lifecycle semantics must first gain a scenario in packages/agent/host/conformance, programmed only against the Host contract. A missing capability gets added to Host — never reimplemented in an adapter. The Host depends on the canonical store but never on the daemon, sidecars, or tuttid.
sessionturngoalruntime-operation send eligibilityterminal statesrecovery
"Does this change define or change the lifecycle semantics of a session/turn/goal/runtime-operation?"
  • Yes → it lives in packages/agent/host; consumers write only delegate code.
  • No (transport, DTO, query, presentation, policy) → adapter.
  • Unsure → ask "would another Host consumer also need this?" If yes, it's Host.
Enforced mechanically: pnpm check:agent-host-boundary ratchets against new *Coordinator/*Worker/*Actor orchestration appearing in adapters.

Adapting the coding agents

One registry, three wire protocols — never a provider switch

There is no per-provider plugin API. Every provider is a declarative descriptor in packages/agent/daemon/providerregistry — identity, runtime kind, auth strategy, capabilities, permission modes, model catalog — and runtime behavior is chosen by the descriptor's strategy enums, never by its name. The registry's own source states the rule: "provider identity must not be used as the constructor switch."

The three adapter families (dispatched on Runtime.Kind)

codex_app_server Codex · Tutti Agent Speaks Codex's first-party app-server JSON-RPC over stdio (thread/start, turn/start, approval requests…). Typed Go bindings (codexproto) are code-generated from OpenAI's own JSON Schema, vendored and pinned to an upstream commit. Replaced the older codex-acp bridge; explicitly not a template for new providers.
standard_acp Cursor · OpenCode · Nexight · Hermes · OpenClaw One shared, data-driven ACP JSON-RPC 2.0 adapter. Each provider is a small declarative config file; quirks are expressed as hooks (stderr mapping, permission-option filtering, mode params) — not subclasses. Third-party Agent Extensions reuse this exact adapter as signed data packages — no code is ever loaded from an extension.
claude_sdk Claude Code The Go daemon drives a TypeScript sidecar (packages/agent/claude-sdk-sidecar) over versioned NDJSON on stdio (verbs: start, exec, guide, cancel, submit_interactive, apply_settings, close). The sidecar wraps @anthropic-ai/claude-agent-sdk and normalizes SDK messages into Tutti activity events. The only Claude runtime path by contract — no parallel implementation allowed.

What every adapter must (and may) implement

All three families produce a Go Adapter with six required methods — Provider · Start · Resume · Exec · Cancel · Close (packages/agent/daemon/runtime/adapter.go). Everything else is capability negotiation: optional interfaces the controller type-asserts for, so a provider gains a feature by implementing an interface, not by adding a branch.

Optional capability interfaces (a sample): TargetedCancelAsyncExec InteractiveGoal PermissionModeLiveSettings ResumeProbeActiveTurnGuidance CommandSnapshot

"Adding a new agent" in practice: write a descriptor — and if it speaks ACP, usually nothing more than a small config file. Only a genuinely new wire protocol requires a new adapter family. The abstraction is kept honest by pnpm check:agent-provider-strategy-boundaries: it scans tuttid, the daemon, and the desktop for provider-name literals (case "codex", == "claude-code", …) and fails CI unless they sit in the registry, generated types, or the explicit allowlist of adapter files. Per-provider differences — capabilities, permission modes, model catalogs, auth flows — reach the GUI only as generated catalogs emitted from the Go registry and cross-validated against the OpenAPI spec, so the UI branches on capabilities, never on names.

Inside the two flagship runtimes

How a turn is actually driven

The two protocols feel similar from the GUI but work very differently underneath: Codex is a long-lived JSON-RPC server that streams notifications; Claude Code is a per-session sidecar feeding a prompt queue into the Claude Agent SDK. In both, approvals are parked server-side and answered by the human — never auto-decided by the adapter.

Codex codex app-server · JSON-RPC

Spawn & handshake
codex is resolved from your PATH and launched as codex app-server; the adapter sends JSON-RPC initialize (client name codex_cli_rs) then the initialized notification.
Open or reattach a thread
thread/start returns a threadId stored as the provider session ID; later runs reattach with thread/resume, replaying token-usage state.
Stream the turn
turn/start responds immediately with "in progress" — the real output arrives as notifications (item/agentMessage/delta, item/reasoning/textDelta, item/started/completed, turn/plan/updated, thread/tokenUsage/updated) that a normalizer turns into Tutti activity events. The turn settles on turn/completed.
Approvals go to the human
Server→client requests (item/commandExecution/requestApproval, item/fileChange/requestApproval, …) park a goroutine, surface a waiting-approval event to the GUI, and map your choice back to accept / acceptForSession / decline / cancel.
Interrupt with teeth
Cancel pauses any active goal, rejects pending approvals, fires turn/interrupt, waits a 3-second grace window — and force-closes the process if Codex doesn't stop.

Claude Code NDJSON sidecar · Claude Agent SDK

One sidecar per session
Go spawns node --experimental-strip-types …/claude-sdk-sidecar/src/main.ts and speaks version-2 NDJSON envelopes over stdio: start, exec, guide, cancel, submit_interactive, apply_settings, close.
Exec feeds the SDK
The exec envelope pushes the prompt into a queue feeding the SDK's query() stream, created lazily inside the sidecar.
Messages normalize on the way up
SDK messages are routed, normalized into sidecar events, and written back line-by-line; the Go adapter forwards them as Tutti activity events and blocks until the turn waiter resolves.
Permissions ride the SDK's control protocol
The sidecar's canUseTool callback emits approval_requested / user_input_requested and blocks on a promise; your answer arrives as submit_interactive and resolves into an SDK allow/deny (optionally with updated input or permissions). bypassPermissions mode short-circuits to allow.
Cancel & close are polite
Cancel rejects all pending interactions; close is a request/ack boundary that waits for SDK shutdown before the process exits.

Provisioning

Who controls which agent version runs

Two opposite philosophies coexist. Claude Code is Tutti-managed: the release pins an exact SDK and provisions a matching CLI binary itself. Codex is user-owned: Tutti runs whatever is on your PATH, enforcing only a minimum version. Both leave the user an escape hatch.

ProviderVersion modelPin / floorBring your own?
Claude Code Tutti-managed The sidecar pins @anthropic-ai/claude-agent-sdk to an exact version (0.3.201 in the current tree). The ~230 MB claude binary isn't bundled — tuttid downloads it (CDN, npm fallback), sha256-verifies it against the SDK's manifest, and installs it under the state dir behind a current.json pointer. Exact SDK pin per release; no minimum-version gate — brief version skew right after an app update is tolerated by design. Yes: CLAUDE_CODE_EXECUTABLE always wins; a PATH-installed claude is the last-resort fallback. Updating your system claude doesn't change the managed default — that moves with Tutti releases.
Codex User-owned Launched straight from your PATH; Tutti detects the version with codex --version and re-checks whenever you update it yourself (brew, npm, …). Hard floor 0.126.0 (capability-derived: the goal-API app-server methods). Below it: CODEX_VERSION_TOO_OLD plus an upgrade wizard showing "current X · requires ≥ Y". Entirely — it's your install. The wizard can also run npm install -g @openai/codex into ~/.local/bin for you, but only on your action.
Cursor · OpenCode User-owned PATH detection (Cursor's binary path is resolved and swapped in at launch). No version floor. Entirely; one-click official install scripts are offered.
Tutti Agent Managed npm package (@tutti-os/tutti-agent), Codex-compatible. — Disabled by default.
How detection works The agentstatus service in tuttid runs the provider checks — CLI present, platform binary, version floor, Node runtime, auth — and the desktop's environment wizard renders staged remediation: the failing check, an inline fix button, the copyable manual command, and an install log. Install budgets are stretched for proxied networks (150 s per registry, 8 min overall; Claude binary downloads get 10 min per source).
Why the asymmetry Claude Code's runtime is an SDK protocol Tutti embeds, so correctness demands the CLI match the vendored SDK — hence managed provisioning with integrity checks. Codex, Cursor, and OpenCode are external CLIs speaking versioned public protocols, so Tutti treats them as user environment: detect, gate on capability where needed, and offer — never force — installation.

Integrated terminal

A real shell, owned by the daemon

The workspace terminal is not an emulated console: tuttid spawns a genuine PTY running your login shell, keeps the session alive independently of any window, and streams it to xterm.js over a dedicated per-session WebSocket. The shared experience lives in @tutti-os/workspace-terminal; the execution substrate stays host-specific.

tuttid terminal service Go
Spawns the PTY with creack/pty — your $SHELL, interactive, TERM=xterm-256color, system-proxy env injected. Owns session state and the output ring buffer.
The wire
One WebSocket per session at …/terminals/{id}/ws. In: input · resize · detach · ping. Out: output · state · gap · exit · metadata. Close is deliberately an HTTP call, not a stream frame.
Renderer surface TS
@xterm/xterm v6 (+ fit, search, serialize, web-links), packaged in packages/workspace/terminal, registered by the desktop as workbench node type "workspace-terminal".

Session semantics worth knowing

Sessions outlive the window, not the daemon Lifecycle: created → starting → running → detached → exited. Closing the window detaches; the process keeps running in the daemon. Reattaching replays buffered output from your last sequence number (~800k-char replay budget, with an explicit gap frame if evicted). Sessions are in-memory only — a daemon restart ends them.
One node = one session, forever The daemon sessionId is part of the workbench node's identity — you can't swap a node onto a different process. New process means new node. Minimize hides; close terminates.
A close guard that actually looks Before terminating, the daemon inspects the PTY's foreground process group (TIOCGPGRP ioctl) and names the running command, so closing a busy terminal asks for confirmation with real information.
Agents use it — but don't run in it Provider login flows (claude auth login, codex login) open a terminal node pre-typed with the command, auto-closed once the provider turns ready (kept open on failure). But agent tool execution is a separate path — the terminal blocks in a conversation timeline are read-only renderings, not live PTYs.

Contract-first

Wherever Go and TypeScript must agree — or Tutti must agree with an upstream vendor — a single source-of-truth generates the code, and a matching check:* guard fails CI if the committed output drifts. Generated code is never hand-edited.

Enforcement

Boundaries that check themselves

The architecture above isn't aspirational — most of it is mechanically enforced by ratchet scripts in tools/scripts/, selected automatically by the changed-aware gate.

pnpm check:changed The single final gate: inspects your diff and selects the relevant tests, typecheck, lint, and boundary checks. Runs as the pre-push hook with --push-ready.
check:agent-host-boundary Keeps lifecycle orchestration out of adapters — the ratchet behind the Agent Host invariant.
check:agent-provider-strategy-boundaries Scans tuttid, the daemon, and the desktop for provider-name branching; provider identity may only appear in the registry, generated types, and the allowlisted adapter files.
check:electron-runtime-boundaries + check:renderer-boundaries Police main/preload runtime imports and renderer feature privacy (services/internal/**).
check:ui-boundaries + check:i18n Ensure UI is built from @tutti-os/ui-system and that no user-visible copy bypasses i18n.
Generated-code guards check:api-generated, check:event-protocol-generated, check:codexproto-generated, check:defaults-generated, check:agent-gui-provider-catalog-generated, check:workbench-go-contract — drift fails CI.
Structural rules Business files ≤ 800 lines; conventional commits with DCO sign-off; docs in docs/architecture & docs/conventions updated in the same change.
Blocking test gates pnpm test:go includes packages/agent/daemon as a blocking lane — timing-sensitive lifecycle tests were stabilized with event-driven synchronization, and adding retries to keep it green is explicitly forbidden.
